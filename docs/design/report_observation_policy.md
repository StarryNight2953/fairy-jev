# 可选报告策略：灌溉后的传感器观测证据

`report_observation_policy="irrigation_recheck_evidence_v1"` 是
`tool_contracts_v2` 上默认关闭的候选文本策略。它修改用户报告工具的参数候选，
不改变工具本体、模型选择问题模板、Agent Loop、任务或验收器。纯 Jev 与 Hybrid
使用同一适配器；原生 LLM 不能启用该 Jev 选项。

## 修复的具体问题

已经结束的 L1 批次中，HN58 运行
`20261020T080417_jev_live_41fe4771` 在 E122 返回响应时间之后、覆盖 43–63 垄的
土壤传感器读数。既有验收接受该覆盖，旧报告模板却仍要求范围状态查询这一特定
路径，于是六次报告均声称“尚未同时确认响应时间后的等待与完整目标区复查”。

此外，原生 `FarmWorldApp._agent_ridge_dict` 会屏蔽 `soil_vwc` 等观测字段。
因此，范围状态查询本身不能当作实际土壤湿度读数。新策略直接使用
`SensorApp.read_soil_sensors/read_soil_sensor` 返回的 `ridge_start/ridge_end/vwc`，
不会通过隐藏字段或传感器名称猜测覆盖范围。

## 证据规则与边界

- 只使用已经实际执行且成功的公开工具结果；必须有可用的动作前后仿真时间。
  未来、失败、未执行或没有时间的读数不作为复查证据。
- 实际灌溉范围来自成功结果的 `irrigated_ridges`，响应时间来自 `effect_ready_at`。
  不从用户任务、请求参数、固有 2 小时常量或 evaluator 填补缺失证据。
- 传感器读数时间必须在该次返回的响应时间之后。范围覆盖来自读数中的实际区域，
  不从请求范围、传感器 ID 或单个代表垄推断完整覆盖。
- 每次灌溉单独记录。后来再次灌溉会有新的响应时间和观测需求，旧复查不能自动
  满足新一次。多个不连续范围也保留缺口。
- 等待工具记录与后续观测分开列出。取得晚于响应时间的读数，不自动编造一条
  等待工具调用。
- 明确标注传感器区域平均值，不宣称每垄实测、含水量达标、农艺恢复或整个任务完成。
- 详细输出最多保留最后 8 次灌溉、每次最后 6 条读数，省略数量明确记录；聚合
  覆盖/部分覆盖/未观测/未知计数仍覆盖全部可见灌溉。所有原始结果继续保存在 trace。
- 原有一般事实报告继续保留，新策略只替换灌溉专项报告部分。不包含灌溉记录的
  工具报告及默认配置保持原行为。

配置示例：

```json
{
  "parameter_strategy": "tool_contracts_v2",
  "report_observation_policy": "irrigation_recheck_evidence_v1"
}
```

manifest 保存策略与模块哈希，候选 `source_refs` 记录策略名。遗漏此配置不会启用。

## 验证结果

全部相关回归 **847 项通过，9.46 秒**，网络连接被禁止。新增检查覆盖读数区域、
时间顺序、失败/未执行、缺失 ETA、异常数值、返回部分覆盖、重复灌溉、等待证据、
观测来源、输入不变及输出省略说明。

原始 HN58 的 6 次报告候选在保留原配置时全部精确重建。加入新配置后，从同样的
公开观测生成新候选，明确列出 E122 的复查来源；原始 trace 哈希前后一致。
这些新候选**没有发送**，没有替换历史模型动作或历史判定。

另外，对纯 Jev 和 Hybrid 各做开启/关闭策略的脚本运行。每次都执行相同的 8 个
原生工具步骤：天气、土壤、库存、目标状态、灌溉、推进 7200 秒、土壤复查、报告。
模型由脚本替代，网络请求为 0：

| 架构 | 策略 | 前四项既有断言 | 报告断言 | scripted_task_success |
| --- | --- | --- | --- | --- |
| 纯 Jev | 关闭 | 全通过 | false | false |
| 纯 Jev | 开启 | 全通过 | true | true |
| Hybrid | 关闭 | 全通过 | false | false |
| Hybrid | 开启 | 全通过 | true | true |

四份轨迹验证和动作回放均通过。以上证明候选文本与已有公开复查证据一致，并能
通过未修改的报告合同；不是新真实模型运行。`live_integration_success` 与
`task_success` 在脚本运行中仍是 null。

## 性能与仍未知的问题

六个冻结窗口中，候选文本 UTF-8 长度均从 **2,842 增至 4,014 字节**，
增加 1,172 字节（约 41.2%）。这只是参数文本长度，不是完整 HTTP 请求大小
或 token 计数。本改动不缩短输入，也不保证模型不再重复发送报告。

是否减少真实循环、是否改善 Hybrid 速度、是否提高自由模型任务成功率，需要新的
受控实验。当前原生 LLM 批次与已批准的 4 次冻结请求均未启用该策略；没有追加真实
模型调用。上下文长度管理和报告的精简表达仍是后续独立问题。
