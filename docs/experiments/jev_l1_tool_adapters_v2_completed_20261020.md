## 上下文超限的直接证据

52 次首次超限全部发生在 **Jev 工具选择请求**。原始响应均明确返回 HTTP 400，
错误类型 `max_tokens_exceeded`。没有将它们归类为 API key、网络超时或任务评分错误。

首次失败请求按同一种紧凑 JSON 重新序列化后的大小：

| 组成 | 最小字节 | 中位字节 | 最大字节 |
| --- | ---: | ---: | ---: |
| 整个请求 | 72,081 | 81,692.5 | 96,528 |
| state | 40,348 | 49,280 | 63,485 |
| questions | 28,400 | 32,999 | 33,002 |

这是 UTF-8 内容尺寸诊断，**不是实际上传字节或模型 token 计数**，不能据此拟合
一个固定的 API 字节阈值。首次失败时历史动作数最少 6、中位 36、最多 110；
单纯限制工具步数不能保证输入可容纳。

按每个失败请求中各工具历史动作的序列化体积累计，最大的来源分别是：

| 历史体积最大来源 | 场数 |
| --- | ---: |
| 用户报告工具 | 21 |
| 范围状态查询 | 19 |
| 收割 | 7 |
| 杀菌剂施用 | 2 |
| 播种 | 2 |
| 杀虫剂施用 | 1 |

这里的“最大来源”不是已证明的唯一原因。实际请求同时携带全历史 state 和全量
工具问题；相同历史还会在工具选择与参数选择阶段重复发送。当前
`task_history_v1` 因而没有在本批次克服上下文频繁超限的问题。

## 工具状态约束仍有缺口

1,124 次错误中：

- 723 次收割返回 `All ridges must be planted before harvest`；
- 235 次播种返回 `One or more ridges are already planted`；
- 其余包括药箱、种子和粮箱资源不足等。

这两类状态错误共 958 次，占全部工具错误约 85.2%。但不能把 723 次全部直接
归因于同一个循环：此前逐次核查确认的是其中 12 场、447 次请求，范围已在
历史成功收割结果中，且原结果确实进入模型输入。可选收割状态合同已对这组冻结
证据做过离线验证，未在当前批次启用，也没有声称必然节省全部 723 次调用。

对播种还需要同样检查：已有种植证据是否可见、是否发生过收割/整地等失效事件、
错误范围是否真正可以从候选中排除。不能只凭错误字符串自动追加永久黑名单。

## HN58：物理闭环通过，报告候选口径发生冲突

运行 `20261020T080417_jev_live_41fe4771` 的五项既有断言：

| 断言 | 结果 |
| --- | --- |
| 灌前天气、土壤、目标状态、配额 | true |
| 精确目标范围与剂量 | true |
| 配额消耗 | true |
| 等待响应后完整复查 | true |
| 事实最终报告 | false |

直接工具链：天气 E11 → 土壤 E21 → 库存 E31 → 43–63 垄状态 E55 →
43–63 垄每垄 0.8 小时灌溉 E86 → 土壤 E96 → 推进 7200 秒 E112 →
土壤复查 E122 → 六次用户报告 E138/E154/E170/E186/E202/E218 →
HTTP 400 E223。

E122 已被现有语义验收接受为响应时间之后的完整目标区土壤复查。但实际发送的
报告候选仍包含：

> 尚未同时确认响应时间后的等待与完整目标区复查。

该文本来自确定性候选生成器，随后由 Jev 选择并真实发送；不是 Jev 自由生成的
事实判断。原候选报告将完整复查识别绑定于范围状态查询，而验收接受传感器返回
的完整覆盖，两者口径不同。六次报告共两种参数文本，都保留了该未完成表述。

因此，本例不能再描述为“未灌前查询”或“未等待复查”。可直接定位的是：
报告候选没有准确表达已经取得的复查证据，模型重复选择报告，最终全历史输入
超限。无法据此证明模型内部为何重复选择，也不能断言修改模板一定完成任务。
原始 evaluator、报告候选和结果均未事后修改。
